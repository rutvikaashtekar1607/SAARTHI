# SEC-01 V2X Cryptographic Specification

## 1. V2X System Overview

V2X (Vehicle-to-Everything) communication enables vehicles and surrounding infrastructure or systems to exchange information.

The V2X environment considered in this threat model consists of:

* Vehicle
* Sensors / Electronic Control Unit (ECU)
* V2X communication network
* Receiving vehicle or infrastructure
* V2X telemetry
* Potential attackers

The purpose of this threat model is to identify security threats to V2X telemetry and classify them using the STRIDE methodology.

---

## 2. V2X Telemetry

Telemetry is information communicated from a vehicle or system to another system.

Examples of V2X telemetry include:

* Vehicle speed
* Vehicle position
* Direction
* Vehicle status

The telemetry travels through the V2X communication path from the transmitting vehicle to the receiving system.

## 4. Trust Boundaries

A trust boundary is a point where data moves between systems, components, or environments with different levels of trust.

For the V2X system, the following trust boundaries are considered:

### TB-01: Vehicle Internal System → V2X Communication

Telemetry generated by the vehicle's sensors or ECU leaves the vehicle and enters the V2X communication environment.

Potential security concerns include:

* Unauthorized modification of telemetry
* Unauthorized injection of messages
* Impersonation of a legitimate vehicle

### TB-02: V2X Communication → Receiving System

Telemetry travels from the V2X communication environment to the receiving vehicle or infrastructure.

Potential security concerns include:

* Message tampering
* Information disclosure
* Message disruption
* Fake or unauthorized messages

### TB-03: Attacker → V2X Environment

An attacker may attempt to interact with the V2X communication environment or its components.

Potential security concerns include:

* Spoofing
* Tampering
* Information disclosure
* Denial of Service
* Unauthorized access

## 5. STRIDE Threat Analysis

The V2X system is analyzed using the six STRIDE threat categories: Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, and Elevation of Privilege.

### 5.1 Spoofing (S)

Spoofing occurs when an attacker pretends to be a legitimate vehicle, device, or system.

#### V2X Threat

An attacker may impersonate a legitimate vehicle or V2X device and transmit messages as if they originated from a trusted source.

#### Affected Area

* Vehicle identity
* V2X communication
* Message source

#### Threat ID

`V2X-S-01`

---

### 5.2 Tampering (T)

Tampering occurs when data is modified without authorization.

#### V2X Threat

An attacker may modify V2X telemetry while it is being communicated between the transmitting vehicle and receiving system.

For example, telemetry such as vehicle speed or position could be changed before reaching the receiving system.

#### Affected Area

* V2X telemetry
* Communication path
* Received data

#### Threat ID

`V2X-T-01`

---

### 5.3 Repudiation (R)

Repudiation occurs when a sender denies having performed an action or transmitted a message.

#### V2X Threat

A sender may deny having transmitted a particular V2X message or performed a specific action.

#### Affected Area

* Message accountability
* Event records
* Sender identification

#### Threat ID

`V2X-R-01`

---

### 5.4 Information Disclosure (I)

Information Disclosure occurs when information is accessed by an unauthorized party.

#### V2X Threat

An unauthorized party may gain access to V2X telemetry while it is being communicated between systems.

#### Affected Area

* V2X telemetry
* Communication channel
* Vehicle information

#### Threat ID

`V2X-I-01`

---

### 5.5 Denial of Service (D)

Denial of Service occurs when legitimate communication or services are disrupted or made unavailable.

#### V2X Threat

An attacker may interfere with V2X communication and prevent legitimate telemetry messages from being delivered.

#### Affected Area

* V2X communication
* Message delivery
* System availability

#### Threat ID

`V2X-D-01`

---

### 5.6 Elevation of Privilege (E)

Elevation of Privilege occurs when an unauthorized entity gains permissions or access beyond what it is normally allowed to have.

#### V2X Threat

An unauthorized device or user may gain higher-level access to V2X system functions.

#### Affected Area

* V2X system access
* Device permissions
* Privileged functions

#### Threat ID

`V2X-E-01`

---

## 7. Security Requirements

The identified STRIDE threats lead to the following security requirements for the V2X environment.

### 7.1 Identity and Authentication

V2X devices and message sources should be authenticated so that unauthorized devices cannot easily impersonate legitimate vehicles or systems.

**Addresses:** V2X-S-01 — Spoofing

---

### 7.2 Message Integrity

V2X telemetry should have mechanisms that allow the receiving system to detect unauthorized modification of messages.

**Addresses:** V2X-T-01 — Tampering

---

### 7.3 Accountability and Event Records

The system should maintain sufficient information to establish the source and occurrence of security-relevant actions or messages.

**Addresses:** V2X-R-01 — Repudiation

---

### 7.4 Confidentiality

Where telemetry contains information that should not be publicly accessible, appropriate protection should prevent unauthorized parties from obtaining that information.

**Addresses:** V2X-I-01 — Information Disclosure

---

### 7.5 Availability and Resilience

The V2X communication environment should be designed to maintain availability and recover from communication disruption or malicious interference.

**Addresses:** V2X-D-01 — Denial of Service

---

### 7.6 Access Control

V2X systems should enforce authorization and least-privilege principles so that devices and users cannot obtain permissions beyond those required for their functions.

**Addresses:** V2X-E-01 — Elevation of Privilege

---

## 8. Cryptographic Security Requirements

The V2X security design shall define cryptographic requirements that address the threats identified in the STRIDE analysis.

### 8.1 Confidentiality

V2X telemetry that contains sensitive vehicle or system information shall be protected against unauthorized disclosure.

### 8.2 Integrity

V2X messages shall include appropriate cryptographic protection so that unauthorized modification of telemetry can be detected.

### 8.3 Authentication

The system shall verify that V2X messages originate from an authorized vehicle, device, or infrastructure component.

### 8.4 Key Management

The cryptographic design shall define requirements for secure key generation, storage, distribution, use, and replacement.

### 8.5 Resource Constraints

Cryptographic mechanisms shall be evaluated against the resource constraints identified for the target system, including computation, memory, code size, and energy consumption.

### 8.6 Cryptographic Selection

No final cryptographic primitive shall be selected solely on theoretical security properties. Selection shall be supported by benchmark evidence and comparison against the defined system constraints.

### 8.7 Security Requirement Mapping

| Security Requirement | Related STRIDE Threat  | Required Protection                             |
| -------------------- | ---------------------- | ----------------------------------------------- |
| Confidentiality      | Information Disclosure | Encryption                                      |
| Integrity            | Tampering              | Message authentication and integrity protection |
| Authentication       | Spoofing               | Cryptographic authentication                    |
| Accountability       | Repudiation            | Secure event/message records                    |
| Availability         | Denial of Service      | Communication resilience                        |
| Access Control       | Elevation of Privilege | Authorization and key/access controls           |

# 9. Cryptographic Benchmark Plan

The cryptographic benchmark evaluates the resource requirements and functional operation of AES-GCM and ECC mechanisms considered for the V2X security design.

The assigned SEC-01 task requires benchmarking AES-GCM versus ECC.

For the ECC benchmark, **ECDH using P-256 / secp256r1** is used as the defined ECC operation because ECC is a family of algorithms rather than a single cryptographic operation.

### 9.1 Benchmark Environment

* Target architecture: ARM Cortex-M4 / STM32F4
* Execution environment: Renode 1.16.0
* Cryptographic library: Mbed TLS 3.6.7
* Compiler: Arm GNU Toolchain 12.2.1

### 9.2 Benchmark Procedure

1. Compile the cryptographic implementation for the target architecture.
2. Execute the implementation in the Renode STM32F4 environment.
3. Verify functional correctness.
4. Measure compiled code size.
5. Record static memory requirements.
6. Record the verified benchmark results.
7. Compare the measured results for AES-GCM and ECDH P-256.

### 9.3 AES-GCM and ECDH Comparison Scope

The comparison considers:

* Functional correctness
* Code size
* Static RAM requirements
* Cryptographic purpose

AES-GCM provides authenticated encryption for V2X data.

ECDH P-256 provides key agreement for establishing shared cryptographic keys.

These mechanisms perform different cryptographic functions and are therefore not directly interchangeable.
